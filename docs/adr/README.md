# 架构决策记录（ADR）

ADR 用来记录已经作出的、会影响系统边界或长期维护的架构选择。它不是讨论区，也不是把实现细节事后补写成合理性的地方。产品方向先看 [`PRODUCT.md`](../../PRODUCT.md)，系统约束看 [`ARCHITECTURE.md`](../../ARCHITECTURE.md)，需要跨范围讨论时先走 [`docs/rfcs/template.md`](../rfcs/template.md)。

## 什么时候必须写 ADR

在实现、采购或启用下列能力前，应有已批准的 ADR：

- 持久化、同步、离线、备份、恢复、删除和保留策略；
- 身份认证、授权、会话、个人/组织边界和第三方访问；
- 加密、密钥/秘密管理和敏感数据隔离；
- 时间、时区、货币、周期、舍入和历史重算口径；
- 计算/规则引擎、预测模型、AI 或外部模型调用；
- 导入、导出、分享、外部连接和数据格式；
- 日志、分析、错误上报、监控和个人数据脱敏；
- 任何可能降低可解释性、可迁移性、用户控制权或历史可重现性的变更。

如果只是一次性、局部且不影响上述契约的实现，可在 PR 中说明“不需要 ADR”的理由；有疑问时按需要 ADR 处理。

## 工作流

1. 先确认问题和产品对齐，必要时创建 RFC；不要把尚未决定的技术偏好写成事实。
2. 当一个具体决策准备进入公开评审时，从 [`template.md`](template.md) 复制模板并分配下一个四位数字编号和简短英文 slug，例如 `ADR-0042-export-format.md`。状态为 `Proposed` 的已提交 ADR 会占用编号；仅存在于个人草稿、尚未提交评审的内容不占编号。本目录的模板不占编号。
3. 写清候选方案、决策驱动因素、数据/隐私/解释影响、兼容性、迁移与回滚。说明哪些是不可变的产品/架构契约。
4. 请求产品负责人和相关技术/数据/安全负责人评审。RFC 的评审不能自动代替 ADR 的批准。
5. 批准后将状态改为 `Accepted`，再在实现 PR 中链接 ADR；实现若偏离决策，先更新 ADR 或创建新的 ADR。
6. ADR 一旦被实现依赖，原则上不删除。新决定取代旧决定时，把旧 ADR 标为 `Superseded`，链接新 ADR，并保留历史。
7. 完成迁移、验证或复审后补写结果。若决定被撤销或过期，记录原因、影响和替代路径。

## 状态与编号

推荐状态：`Proposed`、`Accepted`、`Rejected`、`Superseded`、`Deprecated`。状态必须反映评审事实，不以“代码已合并”代替批准。

文件名格式：`ADR-NNNN-short-slug.md`。编号只递增、不复用；进入仓库评审的 `Proposed`、最终 `Rejected` 或被 `Superseded` 的 ADR 都保留原编号。未提交的个人草稿不占编号。目录索引可在有实际 ADR 后补充；不要为占位而创建 `ADR-0001`。

## 评审门槛

批准前必须能回答：

- 选择如何服务产品任务和价值循环；
- 影响哪些数据、状态、来源、单位、规则版本和历史结论；
- 用户如何理解、纠正、导出、删除或撤回；
- 权限、秘密、日志、第三方和故障降级边界是什么；
- 如何迁移、兼容、回滚，以及如何证明恢复成功；
- 哪些假设尚未验证，何时复审，什么条件会触发新决策。

## 使用模板

复制 [`template.md`](template.md)，删除提示语并填写所有适用字段。不适用的字段写明“无”及理由，不要留空。模板本身不能授权实现；只有状态为 `Accepted` 的具体 ADR 才构成架构决策。
