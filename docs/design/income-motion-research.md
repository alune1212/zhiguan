# 收入数字动效调研

日期：2026-09-23。状态：方案建议，尚未作为产品决定采纳或接入应用。范围仅为收入首页展示；演示使用合成数据，不读取或保存真实个人资料。

## 结论

推荐先验证 **逐位向上滚动的金额 + 紧邻主金额的每秒速率**。效果接近机械里程表（odometer / rolling digits），让变化的数位有连续轨迹，未变化的数位、币符和小数点保持稳定。先只改今日金额，本月累计保持普通文本。

“每秒积累的感觉更明显”是这次设计的待验证假设，不是已有用户研究结论。没有找到足以证明某一种动效是收入看板“最流行”或“公认最佳”的比较研究。可以确认的是，按数位过渡已有原生平台 API、专用组件和实际应用案例，适合作为成熟的设计参照。

用户要感受到工作时间对应的收入积累；继续使用“今日收入估算”“按设定作息估算，非实际到账”。不使用到账通知、收款音效或增加停留时长作为成功标准。边界来自 [PRODUCT.md](../../PRODUCT.md) 与 [PRD-0003](../product/prd/PRD-0003-income-dashboard.md)，本轮已按现行文件复核。

## 当前为什么像时钟

只读代码追踪结果：

- [IncomeApp.tsx](../../src/app/IncomeApp.tsx) 每 1000 ms 更新当前时间，页面恢复时按当前时刻重算；主金额直接替换 `currencyDisplay(todayIncome.decimal)` 文本，没有前后数字的视觉过渡。
- [income.ts](../../src/domain/income.ts) 的 `calculateIncome` 与区间累计按整秒计算。仅把刷新频率提高到 60 fps 不会产生更多有效金额变化。
- [app.css](../../src/styles/app.css) 已有 `tabular-nums` 和减少动态的 CSS 规则；金额已使用 `aria-live="off"`。当前缺少的是数位过渡，不需要更换整个页面或重写收入公式。
- 合成数据检查：8000 元、2026 年 2 月默认作息，10:00:00.000 与 10:00:00.999 均为 50.00 元，后两秒为 50.01、50.03 元。这是当前整秒计算与分位舍入的结果。

## 方案取舍

以下为结合产品边界的设计判断，不是效果实验排名。

| 方案 | 本场景判断 |
| --- | --- |
| 直接换字、整串淡入淡出 | 实现简单，但对增长方向的表达有限；可作为减少动态的降级路径 |
| 逐位滚轮 + 就近速率 | 首选；既有连续变化的视觉线索，又能读懂增长单位 |
| 整串翻牌、每秒弹跳 | 每次变化都重新引起注意，容易继续保留“钟表一拍一拍”的感受；不作为默认 |
| 不断旋转的圆环、扫描光带 | 若与金额没有明确映射，只是在显示时间经过；暂不增加 |
| 飘浮“+金额”、金币、音效 | 可见性强，但容易暗示真实收款并干扰阅读；本轮不做 |
| 加到四位小数、虚构更高速率 | 累计金额仍应显示到分；不能为了运动感改变精度口径或加速金额 |

## 推荐的第一版表现

1. **只有变化的数位滚动。** 正常工作时段内从下方进入、向上滚走，进位自然；不随机转多圈，不给整个金额加缩放或抖动。币符、小数点和未变位保持稳定。
2. **金额仍显示到分。** 分位不能小到难以辨认；使用等宽数字避免左右抖动。速率紧邻主数字，如合成例子的“每秒约 ¥0.014”，并保留估算说明。
3. **先试 800 ms 的过渡。** 这是本轮演示参数，不是行业标准。每秒一次的新目标值，过渡在下一次更新前结束；不加明显回弹。实际体验后再判断是否需要更短或更长。
4. **低速时允许不动。** 几秒才增加一分时，不伪造连续增长。若滚轮和速率仍不够直观，下一步可单独比较“最近一段时间估算增加多少”的静态辅助信息；本轮不预先叠加。
5. **跳变直接就位。** 首次打开、后台恢复、修改资料、跨日归零、时钟回拨或大幅跳变直接显示当前金额，不能补播过去所有增量，也不能强行只增不减。午休、下班和休息日停止增长。

## 可访问性与控制

W3C 对与其他内容并列的自动更新信息要求提供暂停、停止、隐藏或调整更新频率的机制（本质必要情形除外）；自动更新条款没有“五秒以内可例外”的规定。持续滚动也有相应控制要求。详见 [WCAG 2.2 SC 2.2.2 解释](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html)。

建议提供一个“暂停实时展示 / 恢复实时展示”控制，暂停时明确标注“展示已暂停”，避免旧数字被当作当前值；恢复时跳到当前估算，不补播。这仅暂停展示，不改变计算口径或记录工作时间。

同时尊重系统减少动态设置：关闭滚动，直接更新完整金额。**仅关闭动画不能替代自动更新控制**。保留可读取的完整金额文本，滚轮轨道副本对辅助技术隐藏，不逐秒广播；播放、暂停等用户操作才给出简短状态反馈。当前应用的 CSS 减少动态规则不自动证明 JS/Web Animations 组件也会关闭动画，接入时需要验证。

减少动态与更新控制的适用范围可参照 [W3C C39](https://www.w3.org/WAI/WCAG22/Techniques/css/C39)。[ARIA 1.2](https://www.w3.org/TR/wai-aria-1.2/#marquee) 对类似股票行情的非关键、频繁变化信息采用默认关闭实时播报的语义；这里借鉴其播报原则，无需给金额添加 `marquee` 角色。

## 技术落地建议

只改今日金额的展示节点与必要样式，保留领域计算、精确结果、存储与现有按当前时间重算的流程。不要把动画加入共享的 `currencyDisplay`，避免收藏等其他金额也开始滚动。

专用组件首选候选是 `@number-flow/react`；它直接覆盖按位滚动、进位、格式变化和减少动态等需求。若确认只需要简单的旧字滑出/新字滑入，原生 CSS/WAAPI 即可；若选择完整滚轮效果，使用专用组件比维护一套自制滚轮更合适。当前不安装任何依赖，也不为一个数字引入整套 Motion/GSAP。

组件只消费展示值，不能用浮点数逐秒累加收入。若组件要求 JavaScript `number`，需验证当前允许金额范围的分位精度，超出安全范围使用原有完整文本，不以转换丢失精度换取动画。`trend` 只用于正常递增，不覆盖归零、重算和回退语义。

后续最小验证覆盖：9.99 → 10.00、999.99 → 1,000.00、低速不满一分、午休与恢复、跨日与资料重算、减少动态、暂停展示、读屏不刷屏和窄屏不溢出。让用户短暂观看后判断“是否更容易看出积累、是否仍看得清金额、是否知道这不是到账”，不以观看时长替代体验证据。

本轮仅调研与合成动效对比；未修改应用代码、公式、资料或依赖，未开展真实用户实验。合成演示已通过脚本检查，并在浏览器核对桌面与 320px 布局、12 秒结束值及暂停操作；减少动态分支已静态检查，尚未在系统减少动态模式下实机验证。这些检查不代表应用接入或用户效果验收。
