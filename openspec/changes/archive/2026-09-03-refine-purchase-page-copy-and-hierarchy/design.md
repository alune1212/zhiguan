## Context

见 `proposal.md` 的动机和 `specs/purchase-decision-workbench/spec.md` 的用户可观察行为。当前页面把文案、状态标签和结果卡片集中在 `App.tsx`，计算由独立的纯 TypeScript 内核提供，样式由一份 CSS 文件控制。此次变更没有新的数据模型、依赖或外部边界，但自然句子需要根据结果 ID、可用性、证据状态和正负值选择，先明确呈现层职责可以避免把文案需求渗入计算与导出。

## Goals / Non-Goals

**Goals:**

- 用现有组件和 CSS 同步已确认文案与阅读层级。
- 从领域结果派生自然句子，同时保持精确值、状态和原因码不变。
- 让 DOM 顺序、视觉顺序和辅助技术阅读顺序都以工作时间结论为先。
- 用现有测试工具覆盖关键文案分支，不增加依赖。

**Non-Goals:**

- 不修改计算公式、解析、舍入、状态传播或导出结构。
- 不增加输入、页面、账户、存储、网络、提醒或研究能力。
- 不建立通用文案系统、国际化框架、新组件库或设计系统。

## Decisions

### 1. 文案分支留在现有呈现层

在 `App.tsx` 中保留少量纯展示函数，根据现有结果对象生成标题、结论和缺失说明。函数读取结果 ID、`availability`、`evidenceStatus`、`reasonCodes` 与 `exact.decimal`，不得重算任何领域值。

工作时间和金额句子使用 `exact.decimal` 的数字部分，再由句子提供单位，避免把已有 `display` 的单位重复拼接。负数余量通过字符串符号判断并移除开头负号来显示绝对值，不转换成 JavaScript `Number`；零值使用精确十进制字符串判断。领域结果及导出仍使用原值。

替代方案是修改计算内核的 `label` 或 `display`。拒绝该方案，因为这些字段也进入导出，文案调整不应改变领域和公开格式。另建 view-model 模块也被拒绝，目前只有一个页面和少量分支，放在现有文件更小且更容易核对。

### 2. 状态通过句子表达，状态数据继续保留

删除独立状态徽章和总说明。已确认输入显示一次“按你刚刚确认的数字计算”；含大概数时改为“你填了大概数，所以这些结果也都是大概值”。购买后余量用“如果把这笔购买算进本月”表达预测条件。不可用结果根据字段错误和原因码说明缺少什么、影响哪个结果以及下一步。

字段级错误仍紧邻对应控件并通过现有 ARIA 关联。结果区不重复一长串相同错误；它只给出结果级影响。税前收入的余量提示必须要求重新填写到手收入，不能诱导用户只切换下拉框。

替代方案是保留徽章并加更长的统一图例。拒绝该方案，因为它要求用户先学习状态体系，也会继续增加首屏文字。完全隐藏状态同样被拒绝，因为会破坏信任与可解释性。

### 3. 用 DOM 顺序建立主要结果层级

可见结果仍沿用当前过滤条件，但按工作时间、每小时收入、本月可用金额、购买后余量排序。工作时间结果获得单独的主结果 class，CSS 只用现有布局能力扩大其占位、字号和留白；其他结果保持次级卡片。不得依赖 CSS `order` 制造与 DOM 不一致的视觉顺序。

状态徽章和状态帮助块移除后，同时删除对应的未使用样式。保留焦点轮廓、错误文字、可点击面积和窄屏单列布局；颜色不能成为缺失或大概数的唯一提示。

替代方案是重建卡片组件或引入设计系统。当前改动只需要一个主次层级，新增抽象和依赖没有收益。

### 4. 只扩充现有测试面

保留计算测试不变，继续证明公式、精度、局部降级和状态传播没有变化。应用测试更新初始页文案断言，并直接覆盖纯展示函数的工作时间、估算、预测、缺失以及正数、零、负数余量分支。继续使用现有 Vitest 和服务端静态渲染能力，不增加 DOM 测试库。

完成自动化检查后，在本地页面人工核对键盘焦点、展开说明、决定选择、窄屏换行和辅助技术可读顺序。人工检查不替代 `npm run check`，自动化也不代替读屏和真实视觉确认。

## Risks / Trade-offs

- [文案与草案漂移] → 以确认文档为唯一基线，并为关键句和决定映射保留测试断言。
- [展示层误做领域计算] → 只读取 `exact.decimal`、状态和原因码；计算测试保持不变，`calculation.ts` 不进入预期改动。
- [负数格式丢失精度] → 只处理十进制字符串的符号，不转成浮点数，导出继续读取原始领域结果。
- [视觉主次与读屏顺序不同] → 先调整结果数组的 DOM 顺序，再用 class 做视觉强调，不使用 CSS 重排。
- [自然句子变长导致窄屏溢出] → 保留单列断点，检查长错误、税前提示和决定选项的换行。
- [移除徽章后状态不清楚] → 大概数、预测和缺失分别使用明确句子，并保留公式、输入依赖和错误关联。

## Migration Plan

没有数据或格式迁移。实施时先把文案文档状态更新为已确认，再在现有页面中加入呈现函数和文案，随后调整样式与测试。运行完整 `npm run check` 后，用本地页面检查基本输入、可选余量、缺失、负数和五种决定路径。

若验证失败，回退本次文案、呈现函数、样式和测试改动即可；计算内核、用户数据和导出格式不参与迁移或回滚。
